28  Let it draft a small piece you can read and test

This is the first time this course lets the assistant write code you did not type yourself, and it is safe for exactly two reasons. The piece is small enough that you can read all of it, and a test stands behind it before you are allowed to believe it. Take either of those away and the arrangement stops working. A piece too large to read in full cannot be judged, and a piece with no test behind it has only been judged by the same eyes that were about to be fooled.

Every round below follows the same order, and the order is the whole point. Specify first, draft second, read every line third, test fourth. Never let the assistant race ahead of a step you have not done yet.

Specifying comes first because it is the step that decides what correct means. Write down the function’s name, its inputs and its outputs, and one worked example, before you prompt anything at all. The worked example is doing more work than it looks like it is doing, because it forces you to know one answer in advance, and one answer known in advance is the difference between testing a function and merely watching it run.

Then you draft, asking for exactly that one function, giving the assistant the specification and nothing more. Then you read what comes back, line by line, and this step has a hard rule attached to it. If there is a line you cannot explain, stop there. Do not test it, do not run it, and do not accept it. Ask what that line does, or ask for a version without it, because code you cannot explain is code you cannot verify, and accepting it means the whole arrangement has quietly collapsed back into trusting the tone.

Then you test, with one gentle test seeded from your own worked example and one nasty test designed to break the function. Only a passing nasty test earns your belief. A gentle test passing tells you the function is not catastrophically broken, which is worth knowing and is not the same as the function being right.

Warm-up, done together

As a class, specify gc_content(dna) as the fraction of bases that are G or C, with the worked example gc_content('GGCC') == 1.0. Draft it with the assistant. Read it aloud, line by line. Write assert gc_content('GGCC') == 1.0 as the gentle test, and for the nasty test either assert gc_content('') == 0 or a written decision that an empty string is not allowed. Run both.

That last choice is worth pausing on. An empty sequence has no sensible fraction, so there is no answer the machine can tell you here. You have to decide what the function should do and then check that it does it. Deciding, rather than discovering, is what specifying means.

Three small functions

For each function below, follow the full order. Specify with a worked example first, draft, read every line, write one gentle and one nasty test, and run both. Do not move on to the next function until the current one’s tests pass.

Exercise 28-1

AI: Drafter

Specify is_palindrome(dna), returning True if the DNA string reads the same as its own reverse complement. Worked example: is_palindrome('GAATTC') == True. Nasty cases to consider are an odd-length string, and a string containing a base outside A, T, G and C.

Exercise 28-2

AI: Drafter

Specify count_codon(dna, codon), returning how many times a given three-letter codon appears, counting overlaps. Worked example: count_codon('ATGATGC', 'ATG') == 2. Nasty cases to consider are a codon that does not appear at all, and a codon longer or shorter than three letters.

Exercise 28-3

AI: Drafter

Specify most_common_base(dna), returning the single most frequent base in a DNA string. Worked example: most_common_base('GGGATC') == 'G'. The nasty case here is a genuine tie between two bases. Decide in writing, before you draft, what you want to happen in a tie, because last term’s cohort found that the assistant will pick one silently and inconsistently if you do not say. This is the clearest example in the session of a question the code cannot answer for you.

Catch the silent bug

This is the case the whole session is built around. Not every draft that passes a gentle test deserves your belief, and that is the entire reason the nasty test exists. This round is arranged so that the gentle test passes and the nasty one does not, deliberately.

Exercise 28-4

AI: Drafter

Specify gc_content(dna) again, but this time specify that it must be case-insensitive, counting lowercase g and c the same as uppercase. Worked example: gc_content('ggcc') == 1.0. Draft it, read it, and write two tests, assert gc_content('GGCC') == 1.0 and assert gc_content('ggcc') == 1.0.

Many drafts pass the first and silently fail the second, because they count only the uppercase letters, which is the version that appears most often in the text the model learned from. If yours does, do not simply accept a patched version. Reread the fixed line until you can say in one sentence why the first draft missed lowercase input, and notice that you specified the requirement explicitly and got a draft that ignored it anyway. Stating a requirement improves your odds. It does not enforce anything.

Drafting a method, not just a function

Classes have now entered the course, and a method is drafted exactly the way a function is, specified first, read in full, and tested before belief.

Exercise 28-5

AI: Drafter

Specify a small Codon class with an attribute bases and a method translate(self) that returns the corresponding amino acid letter, using a short fixed table of codons that you provide. Four or five entries is enough, and providing the table yourself matters, because a table the assistant supplies from memory is exactly the kind of plausible content that can be quietly wrong.

Worked example: Codon('ATG').translate() == 'M'. Draft the class, read __init__ and translate line by line, and write one gentle test plus one nasty test using a codon that is not in your table. Decide before drafting what should happen in that case, and then check that the draft does what you decided rather than whatever it happened to do.

For your logbook this week, name the one function or method from today where reading it line by line, before testing, made you suspicious enough to write a nastier test than you otherwise would have. Say what specifically in the code raised your suspicion, and whether the nasty test confirmed it or turned out to be unfounded. Both answers are worth having, because a suspicion that proves unfounded is still evidence that you were reading rather than skimming.
