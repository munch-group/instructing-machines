51  AI: Plan before you prompt

By now you know how you can use a set of tests as a specification of how a function should work. The function meets its specification only if it passes all the tests. The nice thing about functions is that, once they are made, you no longer have to care how they work. You just need to which types of values they take as arguments and what type of value they return. This “interface” with the larger program is called the function’s signature. Once you have decided on a functions signature and you have written a slew of tests that define what it should return across an exhaustive range of different inputs, it almost does not matter what is in the function body. It may be implemented in any what that respects the signature and passes all the tests. Having defined what constitutes a correct function body ahead of time, makes it safe to delegate the function body an AI.

A function’s arguments and return value is referred to as its signature and defines its interface to the larger program.

This approach is also how you stay in control when you have the AI help you write a complex program. If you decided to cram the whole thing into a a single function, you would need to write tests that cover all the variations and corner cases of inputs and return values. It would not only be difficult, it would also be hard to assure yourself that you in fact did cover all the cases. And not being completely sure, kind of defeats the purpose of doing the tests in the first place. Instead, you want to break the solution to the problem into smaller functions, each with a defined signature and tests. The smaller each function is, the easier it is to reliably write a set of exhaustive tests. What that means in practice, is that you need to break down the problem yourself before asking the AI to fill in all the function bodies. Fortunately, this is often not that difficult if you understand the problem you are trying to solve. It will also make you realize if you, in fact, do not understand the problem well enough to reliably test result the AI would hand bck to you. This breaking the problem down into functions is called decomposition. You have seen examples of this in the programming projects you have completed so far.

The final product of your decomposition is really just a list of function stubs, with tests that should pass once their bodies have been filled in. Python docstrings will help with your planning for for remembering what each function does. Docstrings are just strings you put on the first line of the function. If formatted correctly, they can be used to generate online documentation, but for our purposes they just contain your own definition of what each function does.

Suppose the task is to take a DNA strand and report its length, its GC content, and whether it counts as GC rich. A plan for it might look like the one below. I have only included tests for the gc_content function here but I am sure you get the idea. If you put into a single file, describe.py, you can run the tests using pytest describe.py in the terminal. You can also add them to a single notebook cell like I did here and use the %%test magic to run the tests (once you have imported im_pytest). The tests will keep failing until all function bodies are filled correctly.

import im_pytest
%%test

def gc_content(dna):
    "Fraction of bases that are G or C. Example: gc_content('GGAT') == 0.5"
    ...

def is_gc_rich(dna):
    "True if more than half the bases are G or C, using gc_content. is_gc_rich('GGGA') == True"
    ...

def describe(dna):
    "A sentence reporting the strand's length, its GC content, and whether it is GC rich."
    ...
    
def test_gc_content_proportion():
    assert gc_content("AAAA") == 0
    assert gc_content("TAGC") == 0.5
    assert gc_content("GCGC") == 1.0
    assert gc_content("CCCC") == 1.0

def test_gc_content_case():
    assert gc_content("aaaa") == 0
    assert gc_content("TaGc") == 0.5
    assert gc_content("GCgc") == 1.0
    assert gc_content("CCcc") == 1.0

def test_gc_content_missing():
    assert gc_content("AANN") == 0
    assert gc_content("TNNC") == 0.5
    assert gc_content("NNCC") == 1.0
    assert gc_content("NNNN") == None

def test_gc_content_empty():
    assert gc_content("") == None

Exercise 51-1

AI: Collaborator

Do the wrong thing once, deliberately, so that you know what it feels like. Take a task made of three or four pieces, such as reading a file of DNA sequences and reporting which one has the highest GC content, and ask the assistant for the whole thing in a single prompt. Do not plan it, do not break it up. Read what comes back and then see if you can test individual pieces of it in isolation, without running the rest. If you cannot isolate any such piece, make that a note to self. Keep this code. You will want to compare it with what you build over the next few exercises.

Exercise 51-2

SOLO

Now Take the same task and write only the decomposition pan, as a set of empty functions with docstrings and no bodies. When you think you are done, check your plan against the standard from earlier: is each piece small enough to read, to test, and to understand on its own?

Exercise 51-3

SOLO

Add at least one test of each each function with input values and the correct return value worked out by hand. You will find that some functions are harder to give an example for than others. A function you cannot easily give an example for is usually a function that is doing too much, that you have not thought through, or both. In that case, consider spitting it into two functions before adding tests.

Exercise 51-4

AI: Collaborator

Show the AI your function stubs and tests and ask it if there are cases you tests do not cover, or if your plan is missing a piece. Go through its suggestions one at a time and accept or reject them. Rejecting a suggestion you understand is a better than accepting one you do not. The exercise should make you feel the difference between using the AI as collaborator, whose opinions you weigh, rather than a designer, whose pre-made decisions you inherit.

Exercise 51-5

AI: Collaborator

Once you have nailed down your plan with function stubs and tests, choose one of the functions that does not call any of your other functions and prompt the assistant for the function body. Verify the result against your tests. As you repeat this for each function, make sure you complete the functions that are called by other functions, before those completing the functions that call them.
