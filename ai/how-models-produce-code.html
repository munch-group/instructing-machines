18  AI: How AIs produce code

A plain, non-technical account of what a model is doing when it writes code and why it may get it wrong.

Back in week one you met the idea that an assistant guesses its next word rather than reasoning about truth, and you saw it guess a stop codon out of a sentence rather than out of an actual sequence. Two weeks of predicting expressions and confirming explanations later, it is worth asking the same question about the thing you will lean on most for the rest of the course: what is the assistant actually doing when it hands you a function?

The answer is: exactly the same thing, token by token, except the tokens now spell Python instead of English. Ask for a function that translates a codon into an amino acid, and the model does not consult a codon table, does not run anything, and does not check its answer against biology. It produces the most statistically plausible next piece of code, given everything you have said and everything like it in its training, one token at a time, until the function looks finished. def, then a plausible name, then a plausible parameter, then a plausible body, each choice made the same way a plausible next word was chosen when it was writing you a sentence.

This is exactly why it is so good at looking right. Function names, docstrings, tidy indentation, a sensible-looking dictionary of base pairs, all of these are things that appear constantly in real, correct code, so the model reproduces that surface fluently and by default. What it has no access to at all is whether the specific logic inside that familiar-looking surface actually computes what the name promises. Nothing in the process of predicting the next plausible token includes running the function and checking the result, because the model is not running anything. It is guessing what correct code tends to look like, not verifying that this particular code is correct.

That gap between looking right and being right is not a flaw that will be patched out of some future version. It is a direct consequence of how the model works, in the same way that a coin does not become less random with practice. A more capable model will guess better, more often, on harder problems, but “guessing better, more often” is still guessing. It can still be fluent, confident, and wrong on exactly the case you needed right, and it will hand you that wrong answer with the same tidy formatting it hands you a correct one. There is no warning light. Nothing about the way an assistant presents a wrong function is different from the way it presents a right one, because from the inside, generating one was no different from generating the other.

This is also why an assistant is not simply the newest, friendliest compiler, even though the ladder in week one might have tempted you toward that reading. A compiler is a deterministic translator: the same source always produces the same machine code, and that machine code means exactly what the source said, because the translation follows fixed rules a person wrote down and proved correct. Ask the same model the same question twice and you can get two different functions back, and neither one comes with a guarantee that it means what you asked. That single difference, guaranteed meaning versus plausible meaning, is why every level below the assistant on that ladder can be trusted the moment it compiles, and the assistant cannot be trusted until you have checked it yourself.

Hold on to the word plausible for the rest of the term; it is carrying a great deal of weight. It is not an insult to the tool, which is often extraordinarily good, and it is not a reason to avoid it. It is an exact description of what its output is, and exact descriptions are what let you build the right habit around them. A plausible answer deserves your attention and often deserves your trust once you have checked it. It never deserves your trust before you have.

Two more Explainer moves

Since week one you have had exactly one permission, AI: Explainer, and you have worked it hard so far as asking what something means. It covers more than that single move, and it is worth seeing two more shapes it takes, because it is worth noticing what they have in common with each other and with the plain version: none of them lets the assistant write code you intend to keep. That is still several weeks away. All of it is about reading, which is the skill everything above it is built on.

Translate it. You may ask the assistant to turn code into plain language, or plain language into code. The catch, and it is the whole exercise, is that you check the translation in both directions. Ask what a line does, get a sentence, then take that sentence into a fresh conversation and ask for the code. If what comes back is not the line you started with, one of the two translations was wrong, and finding out which is the point. A translation that only runs one way is not a translation; it is a guess you happened to agree with.

Ask for more of it. You may ask for more examples of something you half understand, which is a genuinely good use of a machine that has seen a great deal of code. The catch here is the same one as always: you predict what each example does before you run it. An example you cannot predict is not illustrating anything to you yet, it is just more code on the screen.

Both moves are, of course, still governed by the rule you took in week one. The assistant translates and illustrates; the machine says whether it was right.

Exercise 18-1

AI: Explainer

Take this line, which uses nothing you have not met:

print('ATGGCC'[1:4].lower())

Write down in one English sentence what it does, before you run it and before you ask anything. Then give the assistant the line and ask it for one English sentence. Put the two sentences side by side: do they agree, and is one of them vague exactly where the other is precise? Now open a fresh conversation, give it your sentence and nothing else, and ask it for the Python that does what the sentence says. Run what comes back. Is it the line you started with?

Exercise 18-2

AI: Explainer

Slicing is the thing most people half understand at this point in the course, so use it. Ask the assistant for five short examples of slicing the string 'ATGGCC', each showing something different, and ask it for the code only, with no output and no explanation. Do not run them yet. Predict all five first and write your predictions down. Then run all five. You now have two scores: how many of its examples did what it said they would, and how many you called correctly. The second number is the one to put in your logbook.

Exercise 18-3

AI: Explainer

Ask the assistant for a one-line Python function that returns True if a DNA strand is a palindrome (reads the same as its own reverse complement) and False otherwise. Before you run anything, read the function and decide, using only your eyes, whether you believe it is right. Then ask the assistant, in a second message, to explain step by step why its own function is correct. Notice that the explanation is generated the same way the code was, one plausible next token at a time, and is not a proof. Does the explanation change how confident you feel, and should it?

For your logbook this week, describe one moment so far where a fluent-sounding answer from the assistant turned out, on checking, to be wrong, or note that you have not caught one yet, and say what that would tell you about how carefully you have actually been checking.
