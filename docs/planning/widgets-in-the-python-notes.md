# Widgets in the Python notes {#sec-widgets-in-the-python-notes}

This is a review of the twenty-three notebooks and four Quarto files in `docs/python`, read against the source of the four widgets, with an opinion on where each widget would add something the prose cannot do on its own. It is written as a working note, so it names chapters and section anchors rather than speaking in generalities.

## The precondition nobody can skip

Before any widget question can be answered, one fact about the corpus has to be faced. Almost every note in `docs/python` is a single markdown cell. The cell counts are one for biopython, classes, course_tools, data_structures, dictionaries, files, functions, general_exercises, if-else, iteration, list-comprehensions, lists, modules, objects, packages, preface, recursion, testing, tuples and values-operators-logic; two for hello-world, three for getting_started, and nine for precedence-steps. Everything else that looks like code is a fenced block inside prose. Nothing executes, and nothing ever has.

That explains the defect pattern the earlier audit found. The `numbers` and `number[i]` mismatch in `lists.ipynb` survives three repetitions because no cell ever raised the `NameError`. The `is_palindome` misspelling in `testing.ipynb` survives eight repetitions for the same reason. The `print("Second line, file=f")` line in `files.ipynb` and the `open('workfile', 'r')` call with the extension dropped are two runtime faults sitting in a chapter about writing and reading files. The worked example in `course_tools.ipynb` claims that `4 * 8` reduces to `24`. Every one of these is caught for free the moment the code lives in a cell that runs.

So the widget question and the cell-splitting question are the same question. Adopting the widgets turns the notes from a document about Python into a document made of Python, and it does so by forcing the prose apart into cells that have to run. My view is that this consequence is the strongest argument for doing the work at all, stronger than any individual widget's pedagogical merit, and it deserves to be said out loud in the plan.

## What each widget can and cannot do

I read the four widget packages before forming an opinion, because each has constraints that decide which existing exercises can move across unchanged and which need rewriting.

The `steps` widget registers `%%steps` and honours a `# PRINT STEPS` comment tag on individual statements. It walks a single statement one operation at a time and reports each substitution and each reduction. It dispatches on CPython bytecode opcode names through a per-version table, which means it supports Python 3.10 through 3.13 and no other version. The course environment has to pin that range or the keystone chapter stops working. Its command-line twin is `print-steps`, which is the same tool the notes already call `pysteps`.

The `puzzle` widget registers `%%puzzle <result>`, where `<result>` is parsed as a Python literal, not evaluated as an expression. The shuffled lines run in their own namespace, isolated from the notebook. Every line has to be a complete statement at zero indentation, because every permutation the student can produce must at least parse. Blocks are therefore out: no `if`, no `for`, no `def`. The value checked against the expected literal is the value of the last line, so the last line has to be a bare expression rather than a `print` call.

The `script` widget registers `%%exercise`. The cell runs in a fresh namespace and everything it produces, including standard output, standard error, rich display output and any exception, appears in a shaded box under the cell. Nothing the cell defines survives to the next cell, and nothing the notebook has already defined is visible inside it, with one exception: `import` statements reach the live module cache, so importing something the notebook already imported costs nothing and yields the same object.

The `codelens` widget registers `%%codelens` and emits Philip Guo's trace format, rendered by the actual Python Tutor front end inside an iframe. Values are either inline primitives or a reference pair pointing at an object stored once on the heap, which is why aliasing and cycles come out correctly without any special handling: two names holding the same reference draw as two arrows into one box. It shows execution state and standard output and nothing else, so file writes, network calls, plots and turtle drawings are invisible to it. Each instance inlines roughly 850 kilobytes of vendor code, so a chapter can afford a handful of them, not one per exercise.

The division of labour between `steps` and `codelens` falls out of those descriptions, and I think it is the single most useful thing to teach students explicitly. The `steps` widget looks inside one statement. The `codelens` widget looks between statements. When the question is how one expression collapses to one value, reach for `steps`. When the question is what the names and objects look like after a statement has finished, reach for `codelens`. Stating that rule once, in `course_tools`, saves a term of students reaching for the wrong one.

## The steps widget

This widget has a home already built for it, because the substitution and reduction model is the spine of the book and `precedence-steps.ipynb` is its keystone chapter. That chapter currently runs a long sequence of drills whose instruction is to do the steps with pen and paper and then check by adding a `print` at the end: `x = 7` then `y = 4 + x` then `2 + x * x**2 + y - x`; the `a = 4; b = a; c = 2; c = a + b + c` sequence; the degenerate `x = 1; x = x`; the string constructions `microsatellite = "GTC" * 41` and `mini_gene = "ATG" + "GCG" + "TAA"`; `number = 1 / 1 * 4`; `x = 4; y = x + x`; the self-assignment at `{#sec-adding_one}` and its `+=` twin. Every one of these is a `# PRINT STEPS` tag away from producing the trace the prose describes in words. The predict-then-run rhythm survives intact, because the student still commits to an answer first; what changes is that the check now shows the intermediate expressions rather than only the final value, which is what the exercise was always asking them to produce.

The second natural home is the short-circuit material in `values-operators-logic.ipynb`. The reduction list there (`print(True and 4)`, `print(0 and 7)`, `print(-27 and 0.5)`, `print(42 and 0)`, `print("apple" and "orange")`, `print("apple" and "")`, `print(42 or 0)`, `print("apple" or "")`, with one line duplicated) is a set of results with no visible derivation. A student who gets `"apple" and ""` wrong has no way to see where their model diverged. A step trace answers that directly. The same holds for `print(True and "banana" or "orange")` at `{#sec-oneline_ifelse}` and for the ternary construction the chapter presents and then warns against; showing the reduction is a better warning than the prose warning.

Beyond those two chapters I would use it sparingly and deliberately. The one-liner at the end of `lists.ipynb`, `'a'.join('Banana'.split('a')[:3] * 4)[-5:]`, is the best single candidate in the whole book, because the exercise offers three plausible answers and the only way to choose between them without guessing is to reduce it. The coercion drills in `values-operators-logic` (`'9' + '4'`, `'72' * 3`, `'Ba' + 'na' * 2`) and the compound condition in the `if-else` general exercises (`if -4 and 0 or 'banana' and not False`) are worth one trace each.

One thing to check before committing: what the stepper does when a statement calls a function the student defined. If a call reduces in a single step to its return value, that behaviour matches the refrain in `functions.ipynb` that a call is substituted by what it returns, and the nested examples `square(square(2))` and `square(2 * square(1) + 2)` become good `steps` exercises. If instead it descends into the body, the trace will be long and the refrain gets muddied, and I would keep `steps` away from function calls and give that material to `codelens` instead.

Finally, `course_tools.ipynb` should be rewritten around this widget. The chapter already teaches the `# PRINT STEPS` tag and the `pysteps` command, but its transcripts are typed by hand, which is how it ended up claiming that `4 * 8` is `24`, and how the output header came to name `test_studentfile.py` line 4 when the file in the text is `myfile.py` line 3. Making the chapter's own examples run through `%%steps` repairs both faults by construction and demonstrates the widget in the act of introducing it.

## The puzzle widget

Four shuffled-statement puzzles already exist in the notes, and all four satisfy the flat-statement constraint. In `precedence-steps.ipynb` there is the one at `{#sec-puzzle}` that prints `100`, built from `x = x + 4`, `print(x)`, `x = x * 5`, `x = x * x` and `x = 4`; the one that prints `Banana` from `y = 'n'`, `x = 'B' + y + x`, `print(x)`, `x = 'a'` and `y = (x + y) * 2`; the one that prints `9`; and the one that prints `Mogens` from `c = b`, `print(c)`, `a = b + a`, `b = 'og'`, `b = c + a`, `c = 'M'` and `a = 'ens'`. The last two also appear in `general_exercises.ipynb`. Each needs one small edit to move across: drop the `print` line and end with the bare name, so that the widget has a value to compare, and declare the expected literal on the magic line. Those edits are mechanical and I would do them first, because they give four working puzzle cells for almost no effort and let the widget prove itself before anything harder is attempted.

The two best puzzles in the book, though, do not fit. The build-a-dictionary-of-lists exercises in `data_structures.ipynb` at `{#sec-build_lists_fixed}` and its generic twin require the student to reorder lines and also to indent them correctly, because the answer contains a `for` block and, in the generic version, an `if` block inside it. The widget cannot accept those, since a permutation of indented block lines will not parse. This is the one place where I would consider changing the widget rather than the exercise. Reordering plus indenting is a harder and more instructive task than reordering alone, it is the exact skill the block-structure section of `if-else.ipynb` is trying to build, and the two exercises are already written and already known to be solvable. An indentation mode would earn its keep across the loops and conditionals chapters, not only here. If that is more work than it is worth, the alternative is to keep those two on paper and say so, but I would not silently drop them.

New puzzles are cheap to write where the notes already have a sequence whose order matters and whose result is a literal. Three that I would add: the tuple swap in `tuples.ipynb`, as `a = 1`, `b = 2`, `a, b = b, a`, ending on `(a, b)` with the expected value `(2, 1)`, which turns the chapter's closing exercise into something checkable; the dessert list in `lists.ipynb`, where successive `append` and `extend` calls end on the list itself, and where a wrong ordering changes the answer in a way the student can read; and a short dictionary build in `dictionaries.ipynb` ending on a lookup. All three are flat, all three end on an expression, and all three have literal answers.

I would not push the widget further than that. Its answers have to be literals, which rules out floats where formatting is uncertain and rules out anything whose value is an object with a custom representation, and puzzles work best when the ordering is open to more than one plausible reading rather than merely scrambled.

## The script widget

This is the widget with the broadest application and the least drama. Every exercise in the corpus that says type this and run it becomes an `%%exercise` cell. That is most of `values-operators-logic`, `objects`, `lists`, `tuples`, `dictionaries`, `iteration`, `functions`, `data_structures` and `if-else`, which between them hold well over a hundred such exercises.

The argument for it that I find most persuasive is narrower than that, though. These notes plant deliberate errors on purpose, and the isolation the widget provides is what makes those errors fire. A shared kernel is the enemy of a chapter that wants a `NameError`: if an earlier cell defined `numbers`, then the misspelled `number[i]` exercise in `lists.ipynb` may quietly succeed or fail in the wrong way depending on what the student ran before. In a fresh namespace it fails the same way every time, for every student, which is what a teaching example needs. The same applies to the missing-definition demonstration in `values-operators-logic`, the misspelled chorus variable in `functions.ipynb`, and the deliberate syntax faults in `hello-world.ipynb` and `if-else.ipynb`. Once these run, the hand-typed tracebacks can go, which removes the whole class of defects where the shown error message predates Python 3.8.

The isolation cuts the other way too, and the cost should be planned for rather than discovered. Several chapters chain exercises across many cells. In `lists.ipynb`, `desserts.extend(cheeses)` depends on a `desserts` list built two exercises earlier. In `dictionaries.ipynb` the whole nested-family sequence accumulates four dictionaries across the chapter. In `data_structures.ipynb` the guided palindrome walkthrough builds up over several steps. Each of those cells has to be made self-contained, which means repeating a setup line or two. That is a rewrite cost, but it is a cost that pays back, because a cell that must stand alone is a cell whose identifiers can be checked, and identifier drift between prose and code is the most common defect in the corpus.

Two chapters deserve specific decisions. In `files.ipynb`, `%%exercise` cells run in the notebook's working directory, so the write-then-read pair actually creates and reads a file, and the two faults in that chapter would have been caught the first time anyone ran it. I would move the entire chapter into cells and introduce the context-manager form of `open` while doing so. In `hello-world.ipynb` I would do the opposite and hold back. That chapter's subject is the edit, save, run loop in a terminal, and Oath 2 is about a file being read from top to bottom. Moving it into a notebook cell dissolves the thing it teaches. I would keep the first two thirds terminal-first and use `%%exercise` only for the strings and comments material at the end, where the terminal adds nothing.

`testing.ipynb` is the third specific case, and the most important one. The hand-written boolean checks there are already in exactly the shape `%%exercise` wants, and running them would have caught the misspelled function name that appears eight times. More than that, this chapter is where the course argues that tests are how you verify code you did not write yourself, which is the same argument the AI arc makes later. Having the tests run in front of the student, rather than being described, is what makes that argument land.

## The codelens widget

This is the widget with the highest ceiling and the smallest set of correct placements. Its reference model draws aliasing correctly without being asked to, and aliasing is the concept the notes come closest to teaching and then stop short of.

The clearest case is the container exercise near the end of `lists.ipynb`, where `x`, `y` and `z` are assigned, collected into `lst`, and then `x` is reassigned to `'Preben'` and the list is printed again. The prose asks the student to reason about the value of a list being a container of values, and this is the moment where two arrows and one box says in a picture what the paragraph says in three sentences. I would put a `%%codelens` cell there, and I would add the aliasing exercise the chapter never quite reaches: `a = [1, 2, 3]`, then `b = a`, then `b.append(4)`, then print `a`. Predict first, then adjudicate with the picture.

The richest case is `dictionaries.ipynb`. The nested-family exercises there assign one dictionary as a value inside another and then reach through two levels, and then collect all four dictionaries into a list. Four names, several shared references, and a lookup that traverses them: this is the single best payoff for the widget anywhere in the corpus. The chapter is already marked for replacement of its example cast, and the shared-reference structure survives the change to codons or gene annotations without losing anything.

After those two I would use it in five more places. In `functions.ipynb` for scope, on the greeting example with the two names and on the pair of calls that pass different variables into the same parameter, because a frame that appears and then vanishes is what the phrase about a temporary little world is trying to convey. In `iteration.ipynb` on the nested loop at `{#sec-ij_pairs}`, where the two counters advancing at different rates is the whole lesson. In `data_structures.ipynb` on the matrix builder, where a list is appended to a list and then appended to again, and where the picture of rows inside a grid resolves the confusion the code creates. In `classes.ipynb` on the initialiser and attribute assignment for the point example, which is also the cheapest way to give that chapter the exercises it currently lacks entirely. And in `if-else.ipynb` on the nested conditional at `{#sec-nested_if_else}`, though this one is optional and I would drop it if the budget is tight.

Where I would keep it out is as important. It shows execution state and standard output and nothing else, so it has nothing to say about `files.ipynb`, about `hello-world.ipynb`, or about the turtle chapters. It also has nothing useful to say about precedence and short-circuit evaluation, because those questions live inside a single statement and this widget reports between statements. Sending a student to `codelens` for a precedence question teaches them the wrong tool for the rest of the term. And the vendor bundle it inlines means a chapter can carry a few instances comfortably and not dozens, so it should be reserved for the moments where a picture of the heap is the point.

There is one connection already waiting to be made. The debugging chapter in `docs/python/debugging.qmd` has a section headed with confirming by codelens instead of print, and the week seven turtle note describes its own print-based check as the print version of what the codelens widget shows. The vocabulary is already in the later material. Establishing it earlier, in `lists` and `dictionaries`, is what lets those later references land rather than introduce.

## How this ties to the AI thread

The rule the course already states, that the assistant predicts and the machine proves, gives each widget a role in the ladder, and mapping them explicitly would tighten both halves.

The `puzzle` widget belongs to the solo side. Its answer is a single literal and its space of wrong orderings is large, so it is a good place to require that a student commit before any assistant is consulted.

The `steps` widget is the natural instrument for the unreliable narrator role. Ask the assistant to explain what an expression reduces to and why, then run the trace and compare the two accounts step by step. Disagreements are visible at the level of an individual substitution rather than only at the final answer, which is what makes the comparison instructive rather than a bare right or wrong.

The `codelens` widget is the adjudicator for questions about identity and sharing, which is where assistants are least reliable and where students have the weakest intuitions. Asking whether modifying one name changes another, getting an answer, and then looking at the arrows is a complete cycle of the course's central rule in about ninety seconds.

The `script` widget is where drafted code has to survive contact with the interpreter. Anything the assistant writes goes into a cell that runs in isolation, and the shaded output box is the verdict.

## What I would do first

If the whole conversion is too much to take on at once, the order I would choose is this. Rewrite `course_tools.ipynb` around `%%steps`, since it introduces the tool, currently misstates its own output, and sets up the distinction between looking inside a statement and looking between statements. Then convert `precedence-steps.ipynb`, which is the keystone chapter and where `steps` and `puzzle` both pay off immediately, including the four ready-made shuffles that need only a trailing expression. Then `lists.ipynb` and `dictionaries.ipynb` together, because they carry the aliasing material and give `codelens` its two best placements. Then `testing.ipynb`, because it is short, it is the hinge into the AI arc, and running its own examples repairs it. Everything else can follow chapter by chapter, and each conversion will surface its own identifier mismatches as it goes, which is a decent way to work through the copyedit backlog without treating it as a separate task.

Two loose ends to settle along the way. The Python version pin has to be inside 3.10 to 3.13 for `steps` to work at all, and that constraint should be recorded wherever the environment is defined. And `general_exercises.ipynb`, which duplicates a good deal of `precedence-steps` and is already commented out of the chapter list, should be dissolved into widget cells placed next to the concepts they exercise rather than kept as a chapter of its own.
